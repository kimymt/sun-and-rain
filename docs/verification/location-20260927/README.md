# 地点登録・変更

2026-09-27。地名検索、候補の確認、地点変更、選択地点の再読込後の復元を追加。

## 仕様

- 初期地点は東京。日本国内の地名を検索し、地域名・座標を見て候補を選択後、「この地点に変更」で確定する。
- 検索は明示的な送信時だけ。2〜80文字、最大10候補、10秒タイムアウト。入力の変更・ダイアログ終了で古い検索結果を無効化する。
- Open-Meteo Geocodingの`countryCode=JP`、`language=ja`。応答の国コード・座標・名前も確認する。住所・建物名検索、現在位置取得、地図は今回追加していない。
- 地点は名前と緯度経度、ID、座標改訂番号で管理。同じ座標を選び直した場合はIDと改訂を維持。座標が変われば改訂を進め、前地点の表示値・比較元をリセットする。
- 予報取得の世代番号を地点変更時に更新する。古い地点の応答が遅れて届いても採用しない。送信済みのネットワークリクエスト自体は停止しない。
- 選択地点は予報取得の成否とは独立して保存する。保存できない場合は画面内だけで変更し、再読込後には残らないことを知らせる。

既存IndexedDBの`locations`ストアへ、キー`__settings`の選択地点レコードを追加した。予報レコードの形式やDB版は変更していない。既存の東京レコードを保持し、初期版の登録枠は`primary`の1枠。異なる登録地点の履歴を無制限に蓄積しない。地点ID別の保存構造は将来の複数地点に使える。

## 実APIで判明した検索制約

公式仕様では2文字は完全一致、3文字以上は前方一致。実測で「札幌」はHTTP 200・候補なし、「札幌市」と「Sapporo」は札幌市の候補を返した。UIに正式な市区町村名またはローマ字での再検索を案内する。住所検索のような網羅性を保証しない。

最初の実ブラウザ試験は「札幌」の候補を待ってタイムアウトした。通信障害とは断定せず、API本文を確認して検索語による差を特定した。「札幌市」で再実行し、実APIの候補選択・予報取得・保存まで成功した。
