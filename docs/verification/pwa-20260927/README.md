# PWA・オフライン起動

確認日: 2026-09-27。verify-changesとverify-pwa-lifecycleの確認観点で実施。

## 実装

- Web App Manifest: standalone、相対start_url・scope・id、192/512pxアイコン。
- iPhone向け180pxアイコンと画面下部のホーム画面追加案内。
- Service Worker: 同一オリジンのアプリ本体12ファイルだけを版ごとに保存。予報・地名検索APIはCache Storageに保存しない。
- 予報・地点は既存のIndexedDBを使用。オフライン再起動で復元する。取得時刻、古い値、取得失敗を表示し、予報の鮮度を更新しない。
- 準備完了は、ページの制御と全キャッシュファイルの存在を確認した後に表示する。
- 通信断の表示と、初回・未保存・期限切れには通信が必要である旨を追加。

## 更新方式

`scripts/build-sw.mjs`が全アセットのSHA-256を埋め込んだ`app/sw.js`を生成する。アセットまたは生成処理が変わるとキャッシュ版が変わる。`--check`で生成物の古さを検出する。

インストール時に全ファイルを取得し、本文のハッシュを照合する。一つでも失敗・異なる版なら更新を不採用にし、現在の版を維持する。正常な更新は待機し、全ての既存アプリページが閉じられた後に有効になる。skipWaitingによる操作中の強制切替はしない。更新案内から全タブ・ホーム画面のアプリを閉じて開き直す。

有効化で旧アプリキャッシュだけを削除し、IndexedDBは維持する。稼働中の版のキャッシュが不足した場合も、ネットワークから取得した本文のハッシュが合わなければ混在したファイルを返さない。

起動時の登録と、前面復帰時に前回確認から1時間以上経過していれば更新確認を行う。通知・Push・バックグラウンド予報取得は追加していない。

## 検証結果

確認範囲内で成功。

- [PWAライフサイクル7シナリオ](results.json): Chromiumで実際にService Workerを登録し、BrowserContext.setOfflineで通信を遮断。APIRequestContextやnavigator.onLineの書換えによる代用ではない。
- 登録地点を札幌へ変更し保存。オフラインで再読込・タブを閉じて再起動しても地点と数値を復元し、時間選択を操作できた。
- 不完全な配信（CSS本文が埋込みハッシュと不一致）を拒否。旧版はオフラインでも起動した。
- 更新版は既存ページを強制再読込せず待機。全ページを閉じて開き直した後に変更したHTMLを表示し、地点・予報を維持。旧キャッシュ削除も確認した。
- アプリ本体だけ準備済みで予報が未保存の場合は欠損表示。初回の完全オフライン訪問はネットワークエラーになり、予報を捏造しない。
- [57件のNodeテスト](unit-results.txt)、[4画面幅の既存操作テスト](browser-results.json)、[保存・比較9シナリオ](persistence-browser-results.json)も成功。
- [オフライン画面](pwa-offline-390.png)。予報APIと地名APIは模擬応答。更新用テストサーバーでHTMLとハッシュ・キャッシュ版を変更している。

更新案内の初回テストでは、workerがinstalledになる前後の状態を扱いきれず案内が非表示のままだった。installedイベントからも準備完了を反映するよう修正し、再実行した。

初期の試験ではブラウザをオフラインにしてもPlaywrightの模擬APIが応答していた。画像で取得成功表示が残ることを発見したため、通信遮断と同時に模擬APIも失敗させるよう変更した。最終試験は取得失敗・以前の取得値の表示も検証しており、オフライン中の新しい模擬応答を保存復元の証拠にしていない。

## 配信と費用

現在はローカル検証のみ。追加の契約・配信先・依存パッケージはない。Service WorkerにはHTTPSが必要で、ローカル検証ではlocalhostの例外を利用する。配信時は専用オリジンのルートへ`app/`全体を同じ版として配置する。アセットを変更したらService Workerを再生成する。途中配信で検証が失敗した場合も旧版を使用できるが、原子的な配信が望ましい。

新しい版の準備はアセット12リクエストとSW確認。通常利用はキャッシュを使用する。気象APIの取得頻度は変えていない。キャッシュはブラウザの削除・退避で失われ得るため、永続的なオフライン起動を保証しない。
